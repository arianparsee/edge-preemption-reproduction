# محاسبه دستی سناریوی کوچک مرحله نهم

## 1. وضعیت شواهد

- `[آزمون کمکی]` اعداد این سناریو پارامتر آزمایش مقاله نیستند؛ فقط برای کنترل دستی موتور ساخته شده‌اند.
- `[فرض بازتولید؛ تأییدشده]` Deadline فراگیر است.
- `[فرض بازتولید؛ تأییدشده]` روابط flow فقط برای server منتخب ارزیابی می‌شوند.
- `[پیشنهاد فنی]` تصمیم‌ها scripted هستند؛ هیچ KG/DK، tie-breaking یا preemption price نامشخصی استفاده نمی‌شود.
- ترتیب eventها با `(time, order)` صریح شده و موتور ترتیب پنهانی انتخاب نمی‌کند.

## 3. محاسبه دستی گام‌به‌گام

### زمان 0

1. `task-a`, `task-b`, `task-d` وارد می‌شوند.
2. `task-a` روی `server-1` پذیرفته می‌شود:
   - قبل: `(10,10,10,10)`
   - مصرف: `(6,4,2,2)`
   - بعد: `(4,6,8,8)`
   - fit price صریح: `0.9×10=9`
3. `task-d` روی `server-2` پذیرفته می‌شود:
   - قبل: `(4,4,4,4)`
   - مصرف: `(4,4,4,4)`
   - بعد: `(0,0,0,0)`
   - fit price صریح: `0.9×12=10.8`
4. `task-b` رد می‌شود:
   - روی `server-1`، storage لازم 5 ولی residual برابر 4 است.
   - روی `server-2`، residual همه منابع صفر است.

### زمان 1

1. `task-c` وارد می‌شود.
2. روی residual فعلی `server-1` جا نمی‌شود، چون `7>4` در storage.
3. با آزادسازی `task-a`، منابع `server-1` دوباره `(10,10,10,10)` می‌شوند.
4. `task-a` preempt و Utility کسب‌شده آن صفر می‌شود.
5. `task-c` پذیرفته می‌شود:
   - قبل از پذیرش پس از release: `(10,10,10,10)`
   - مصرف: `(7,5,2,2)`
   - بعد: `(3,5,8,8)`

این preemption scripted است؛ شرط 5٪ و قیمت preemption استفاده نشده‌اند.

### زمان 2

`task-d` هنوز active است، ولی `2 > 0+1`. با Deadline فراگیر نیز دیر شده است:

- state → `EXPIRED`
- Utility کسب‌شده → 0
- منابع `server-2`: `(0,0,0,0) → (4,4,4,4)`

### زمان 3

`task-c` در `3 = 1+2` کامل می‌شود. چون boundary فراگیر تأیید شده است:

- state → `COMPLETED`
- Utility کسب‌شده → 30
- منابع `server-1`: `(3,5,8,8) → (10,10,10,10)`
